# 完成前的校验

## 概述

**核心原则：** 始终以证据为先，再作断言。

**违背规则的字面，即是违背规则的精神。**

## 铁律

```
未经全新的校验证据，不得声称完成
```

若在本条消息中未运行校验命令，则不得声称其已通过。

## 门禁流程

```
在声称任何状态或表达满意之前：

1. 识别：哪条命令能证明该断言？
2. 执行：完整执行该命令（全新、完整）
3. 读取：完整输出，检查退出码，统计失败数
4. 核验：输出是否印证该断言？
   - 若否：如实陈述实际状态并附上证据
   - 若是：附证据再作断言
5. 仅在此之后：方可提出断言

跳过任何一步即等同于撒谎，而非校验
```

## 常见失效场景

| 断言 | 所需证据 | 不充分的依据 |
|-------|----------|----------------|
| 测试通过 | 测试命令输出：0 失败 | 历史运行结果、“应该能过” |
| Lint 干净 | Linter 输出：0 错误 | 局部检查、推断外延 |
| 构建成功 | 构建命令：exit 0 | Linter 通过、日志看起来正常 |
| 缺陷已修复 | 复现原症状的测试：通过 | 已改代码、想当然认为已修 |
| 回归测试有效 | 红绿循环已验证 | 仅通过一次 |
| 代理已完成 | VCS diff 显示有变更 | 代理报告“成功” |
| 需求已满足 | 逐项核对清单 | 测试通过 |

## 危险信号 - 立即停止

- 使用“应该”“大概”“似乎”等不确定表述
- 校验前就表达满意（“太好了！”“完美！”“搞定了！”等）
- 未经校验就准备 commit / push / 提 PR
- 轻信代理的成功报告
- 依赖局部校验
- 心存“就这一次”的侥幸
- 因疲惫而想草草收工
- **任何未运行校验就暗示成功的措辞**

## 防止自我合理化

| 借口 | 事实 |
|--------|---------|
| “现在应该能行了” | 去运行校验 |
| “我很有把握” | 把握 ≠ 证据 |
| “就这一次” | 没有例外 |
| “Linter 过了” | Linter ≠ 编译器 |
| “代理说成功了” | 需独立核验 |
| “我太累了” | 疲惫不是理由 |
| “局部检查就够了” | 局部证明不了任何事 |
| “换个说法就不算违规” | 重精神而非抠字眼 |

## 关键模式

**测试：**
```
✅ [执行测试命令] [看到：34/34 通过] “所有测试通过”
❌ “现在应该能过了” / “看起来是对的”
```

**回归测试（TDD 红绿循环）：**
```
✅ 编写 → 运行（通过）→ 回退修复 → 运行（必须失败）→ 恢复 → 运行（通过）
❌ “我已写好回归测试”（未经红绿验证）
```

**构建：**
```
✅ [执行构建] [看到：exit 0] “构建通过”
❌ “Linter 过了”（Linter 不检查编译）
```

**需求：**
```
✅ 重读方案 → 创建核对清单 → 逐项核验 → 报告缺口或完成情况
❌ “测试通过，阶段完成”
```

**代理委派：**
```
✅ 代理报告成功 → 检查 VCS diff → 核验变更 → 报告实际状态
❌ 轻信代理报告
```

## 适用时机

**始终在以下动作之前：**
- 任何形式的成功/完成断言
- 任何满意度的表达
- 任何关于工作状态的肯定性陈述
- 提交、创建 PR、任务收尾
- 进入下一项任务
- 委派给代理

**规则适用于：**
- 准确措辞
- 改写与同义词
- 暗示成功
- 任何暗示完成/正确的沟通
